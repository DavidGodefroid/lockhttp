FAQ

Pre-release. lockhttp v0.8.0 is out as a pre-release and runs in Docker only (one lockhttp launcher, a cosign-signed image): command names are fixed, flags may still move. TLS decryption ships in it and is optional, wired by lea: without a local CA and the signer (--ca-cert, --signer), HTTPS is decided at the domain. Design decisions: docs/decisions.md, contract with lea: docs/lea.md.

Is lockhttp ready to use?

It is a pre-release: v0.8.0 is out, built on lockkit v0.13.0. Try it, report what breaks; flags may still move before a stable release.

Do I need lea?

Yes, for now. lockhttp relies on lea’s topology: each agent container on its own internal network, a proxy container as the only way out, and a source map naming the container behind each address. The gate is a plain HTTP(S) proxy, but the guarantee comes from that topology.

Why not a simple domain allowlist?

Because an allowed domain is allowed for reads and writes. lockhttp keeps reads of trusted hosts free and stops writes, uploads and unknown hosts for a human, with a trace of who asked.

What happens when nobody answers?

Requests that need a human are held 60 s, then refused with E_PENDING; the ticket stays pending on the hub and the same request goes through once you approve it. When the hub ticket expires unanswered, the agent gets E_TIMEOUT. With no console running (lox up starts it), they are refused at once with E_NO_CONSOLE, while trusted reads continue.

Does lockhttp decrypt my traffic?

Only if you turn it on. Without it, lockhttp decides HTTPS on the host name and port (CONNECT and SNI). With a CA generated per installation (lockhttp ca init), trusted only inside lea’s containers, and the signer that holds its key, the gate decrypts and decides each request. Hosts that pin their certificates go in a splice list and stay decided at the domain.

Can the agent approve its own request?

No. Approvals happen only on lockhub, outside the agent’s containers: in lox approve, lea’s deck or a paired phone. Each held request is a NeverAuto ticket, the hub signs your decision and the gate checks it. The agent cannot reach the hub: its containers are not on the hub’s network, and the gate refuses the hub’s addresses as targets.

Can I let some requests through without asking?

Yes: a free rule, written and confirmed by you in the console’s review, scoped to a container or to all. An auto rule stays valid in the policy (and some classes, such as uploads, messaging, publishing and pushes, can never be auto), but under the hub it asks like ask: every held request is a NeverAuto ticket a human answers.

Is there an MCP server?

No, not yet. Agents meet lockhttp as a proxy; its refusal pages tell them what to ask of you.

Which licence?

Apache 2.0, like the rest of the Lock family.
