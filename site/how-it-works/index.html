How it works

How lockhttp works

Two planes on two sides of a boundary. Only the human side can say yes.

The data plane, lockhttp gate, is a proxy beside lea’s proxy container. The control plane, lockhttp console, runs in a container of its own, under its own account: it serves the policy and asks you about every loosening.

Requests that need a human become signed tickets on lockhub. You answer them in lox run, lox approve, lea’s deck or a paired phone.

The agent containers never see the console socket, and never join the hub’s network. The gate refuses the hub’s addresses as targets.

The console authenticates the gate by its uid (SO_PEERCRED) and never goes on the network itself.

How a request is decided

The first step that decides wins:

  1. Network floor (deny, cannot be loosened): IP literals, DNS over HTTPS, private ranges and metadata addresses, ports other than 80 and 443, an SNI that differs from the host, Upgrade: h2c, nested CONNECT.
  2. Internal hosts you declared (CI, registry): decided at the domain, on their declared ports. Free only when you marked them read.
  3. A single-use authorisation, left by an approval whose client had already given up.
  4. Exfiltration heuristics (data in the URL, high-entropy values, unusual headers, known secrets, PII). Logged only by default; with heuristics = "enforce" a score of 3 or more asks.
  5. Policy rules, from the most specific to the least.
  6. Defaults: body-less reads of trusted hosts are free. Reads of unknown hosts, writes, uploads, messaging and WebSockets ask. A body over the buffer limit (10 MiB) is denied.

The full evaluation order: the policy reference.

The life of a held request

  1. Agent → gate: POST https://api.unknown.io/v1/upload
  2. Gate: source → container; policy → ask; body buffered (up to the limit)
  3. Gate → hub: a signed NeverAuto ticket with the summary, a masked preview, warnings and who asked (container, agent, task, session)
  4. Hub → you: the approval screen in lox run (or lox approve, lea’s deck, a paired phone)
  5. You → hub: y, or n <reason>. The hub signs the decision and the gate checks it.
  6. Gate → upstream: the held request on y, or 403 E_DENIED with your reason

The gate holds a request for 60 s. If nobody answered by then, the agent gets 403 E_PENDING and the ticket stays pending. Once you approve, the same request (same fingerprint) goes through once, within 10 minutes.

Without a console, an ask is refused at once with E_NO_CONSOLE. Free traffic continues on the last approved policy.

HTTPS, with or without decryption

ModeWhat the gate seesWhat you approve
CONNECT + SNI (no CA)host, port, SNIA host for a container: y opens container × host × port for 10 minutes, reads and writes, content unseen. The screen says so.
TLS decryptionmethod, path, headers, bodyOne request. A local CA, trusted only inside lea’s containers, is made per installation; lockhttp signer holds its key.

Hosts in the policy’s splice list (clients that pin their certificates) and internal hosts are never decrypted. They are decided at the domain, and never answered without a human.

LLM APIs as a relay

A model API can reach far beyond the model. On the Claude API, mcp_servers makes the provider call any remote MCP server, and some server tools fetch or run things outside your machine.

lockhttp checks the Claude API per request once TLS is decrypted:

  • POST /v1/messages and /v1/messages/count_tokens pass only without mcp_servers or container, and with no server tool other than web_search;
  • /v1/files* asks;
  • a credential that is not one of the container’s own is denied (E_SECRET_EGRESS);
  • any other path or host under the Anthropic domains asks, never answered without a human.

Every rule: the policy reference.

Credentials the agent never holds

A policy inject entry has the gate add a header, such as Authorization: Bearer …, for one exact host and port. The secret comes from the gate’s own secrets file.

The agent sends its request without the credential. A request that carries the injected secret itself is refused with E_SECRET_EGRESS; a missing secret, with E_INJECT.

[[profiles.default.inject]]
id         = "home-assistant"
host       = "homeassistant"
port       = 8123
header     = "Authorization"
scheme     = "Bearer"
credential = "ha-token"   # its name in the gate's secrets file

Paths, methods and containers: credential injection.

Rules

The policy lives with the console, never in the project. The gate reads no policy file: it uses what the console serves.

A rule applies to all containers or to one, never to an agent: an agent name is a claim, not an identity.

[[profiles.default.rules]]
id      = "github-api-read"
host    = "api.github.com"
methods = ["GET", "HEAD"]
verdict = "free"

[[profiles.default.rules]]
id        = "npm-audit"
container = "lea-ab12cd34ef"
host      = "registry.npmjs.org"
methods   = ["POST"]
path      = "/-/npm/v1/security/advisories/bulk"
verdict   = "ask"
max_body  = "256KiB"

Any loosening (a new host, a wider method or path, ask to free, a wider scope) waits for your confirmation in the console’s :review.

An auto rule stays valid but asks like ask: every held request is a NeverAuto ticket. Uploads, messaging, registry publishing, git-receive-pack, spliced hosts, heuristic hits, secrets and production profiles can never be auto.

Refusal codes

A refusal is a 403 with X-LockHTTP-Code and X-LockHTTP-Request headers, and a text body saying why and what to ask. The codes are part of the protocol and never renamed.

CodeMeaningAgent should
E_PENDINGthe request waits for the human past the hold timeretry the same request in a moment
E_DENIEDthe human denied the request (the reason is in the body)not retry; ask the user
E_TIMEOUTthe hub ticket expired before anyone answeredsend the same request again: it is asked again
E_NO_CONSOLEno lockhttp console is runningask the user to start it
E_RULEa deny rule or the deny list refuses itask the user to change the rule
E_FLOORIP literal, DoH, cloud metadata, port, SNI or Host mismatch, h2c, nested CONNECTuse a named public host on 80 or 443
E_SECRET_EGRESSa credential leaving its own hosts, or the value of a secret the gate injectsnever send a credential to another host
E_BODY_TOO_LARGEthe body is over the buffer limitsend less, or ask for a rule
E_SOURCE_UNKNOWNthe gate cannot tell which container sent the requestuse the proxy address lea gave
E_INJECTthe policy injects a credential for this host, and the gate lacks itask the user; never send the credential itself

Also registered: E_HOST_UNKNOWN, E_METHOD, E_EXFIL_SUSPECT, E_CLAUDE_API_PARAM and E_PINNED (in the gate’s audit only).
